# Безопасная установка и обновление Dostup VPN для Linux

**Статус:** согласовано
**Дата:** 19 августа 2026 г.
**Область:** `dostup-install.sh`, Linux CLI, README и Linux-инструкция

## Цель

Устранить риски повреждения рабочей Linux-установки при установке, переустановке и
`dostup restart`, не усложняя пользовательский процесс и не изменяя существующее
преобразование импортируемого профиля.

## Зафиксированные ограничения

- systemd-сервис продолжает работать от `root`; смена пользователя и hardening в
  эту работу не входят.
- Официальная установка остаётся одной командой.
- Команды управления сохраняют привычную семантику.
- Обработка профиля не меняется:
  - удаляются `external-ui`, `tun`, `rule-providers` и строки `RULE-SET`;
  - `external-controller` сохраняется, а bind `0.0.0.0` ограничивается loopback;
  - DNS listen, mixed-port и финальный `MATCH,Auto Select` обрабатываются как сейчас;
  - `proxy-rules` и новые правила не добавляются.
- Недоступность одного источника не блокирует безопасное обновление другого
  компонента.

## Команды и блокировка

Все изменяющие команды используют один неблокирующий `flock`. К ним относятся
`start`, `stop`, `restart/update`, `update-providers`, `rollback`,
`uninstall` и повторный запуск установщика. При занятой блокировке второй процесс
немедленно завершается с сообщением «обновление уже выполняется» и кодом `75`.

`status`, `check`, `healthcheck`, `log` и `help` остаются неблокирующими.

## Транзакционная модель

Установка, переустановка и обновление используют общий механизм:

1. При работающем сервисе создаётся `/opt/dostup/.staging.<pid>` на том же
   filesystem.
2. Кандидат начинается с копии текущего known-good комплекта.
3. Ядро и профиль обновляются независимо:
   - ядро выбирается по точному имени GitHub release asset;
   - архив скачивается во временный файл;
   - обязательный `assets[].digest` должен иметь формат `sha256:<64 hex>`;
   - digest сверяется до распаковки, а gzip проверяется до замены бинарника;
   - профиль проходит строгую URL-проверку, скачивание во временный файл и прежний
     `process_config()`.
4. Если компонент недоступен или повреждён, кандидат сохраняет его текущую рабочую
   версию. На первой установке ядро и профиль обязательны.
5. Полный кандидат проверяется staged-бинарником:

   ```bash
   staged_mihomo -t -d staged_runtime -f staged_config
   ```

6. Если ни один компонент не изменился, сервис не перезапускается.
7. Только после успешной проверки сервис останавливается, текущий комплект
   сохраняется как known-good, а staged-файлы устанавливаются через `mv` внутри
   одного filesystem.
8. Настройки `installed_version`, `proxy_port` и другие метаданные фиксируются
   только после успешного локального healthcheck.

При обработке staged-профиля порт, занятый текущим процессом Dostup, считается
доступным кандидату. Это сохраняет нынешний результат импорта: работающий старый
сервис не должен заставлять новый профиль выбирать другой порт.

Существующая `/opt/dostup` перед переустановкой не удаляется. Ошибка сети,
зависимостей, проверки или нового профиля оставляет установленный сервис без
изменений.

## Runtime и Geo

Mihomo запускается с явным каталогом:

```ini
ExecStart=/opt/dostup/mihomo -d /opt/dostup -f /opt/dostup/config.yaml
```

Однократная миграция переносит из `/root/.config/mihomo` только отсутствующие
runtime-файлы: Geo/ASN, cache и каталоги провайдеров. Legacy-`config.yaml` не
копируется. Исходный каталог сразу не удаляется и остаётся страховкой миграции.

Geo и ASN загружаются во временные файлы и заменяются атомарно. Если release API
публикует digest, он обязателен. Ошибка обновления сохраняет прежние файлы; частичная
загрузка никогда не заменяет рабочий файл.

## URL-политика подписки

- Публичные подписки разрешены только по HTTPS.
- HTTP разрешён лишь для `localhost`, loopback, RFC1918 IPv4 и локальных
  IPv6-диапазонов.
- Произвольное доменное имя по HTTP запрещено, даже если в момент проверки оно
  резолвится в приватный адрес.
- На первой установке недопустимый URL отклоняется до любых изменений.
- При обновлении уже сохранённый публичный HTTP-URL не запрашивается: используется
  текущий профиль, выводится ошибка компонента, а независимое обновление ядра может
  продолжиться.
- HTTP status уже проверяется через `curl -f`. Content-Type используется только
  как диагностическая информация и не является строгим критерием.

## Known-good и rollback

Хранится один предыдущий рабочий комплект: ядро, обработанный профиль, используемые
Geo-файлы и согласованные метаданные настроек. Следующее успешное обновление заменяет
этот резерв, поэтому занимаемое место не растёт.

Команда `sudo dostup rollback` меняет текущий и резервный комплекты местами,
запускает сервис и выполняет локальный healthcheck. Благодаря обмену комплектов
повторный rollback отменяет предыдущий ручной откат.

При провале запуска нового комплекта автоматический rollback:

1. останавливает неудачный сервис;
2. возвращает known-good файлы и настройки;
3. повторно запускает сервис;
4. выполняет локальную проверку;
5. при повторном провале сохраняет оба комплекта и выводит критическую ошибку с
   последними строками journald.

## Post-update healthcheck

Жёсткие локальные проверки определяют необходимость автоматического rollback:

1. `systemctl start` завершился успешно;
2. процесс остаётся активным несколько секунд;
3. итоговый mixed-port слушается процессом Mihomo;
4. если профиль содержит `external-controller`, проверяется его фактический
   loopback-адрес и порт. Ответ `401` при `secret` считается подтверждением
   доступности API.

После этого выполняются мягкие проверки: внешний запрос через proxy и healthcheck
доступных провайдеров. Их ошибка выводит предупреждение, но не вызывает rollback,
поскольку внешний сайт или провайдер может временно не отвечать.

## Канал установщика

Стабильный установщик публикуется как versioned GitHub Release asset, например
`installer-v1.0.0`. `master` остаётся каналом разработки и автоматически не
исполняется.

Официальная команда скачивает
`releases/latest/download/dostup-install.sh` в файл и запускает его. До любых
изменений установщик определяет собственный release и проверяет свой файл по
`assets[].digest`. Документация также содержит pinned-команду для конкретного тега.

Самообновление показывает текущую и новую версии, скачивает release asset,
проверяет digest и только затем запускает новый установщик. Версия и результат
обновления записываются после успешной транзакции.

## Тестирование

Быстрые тесты:

- `bash -n` и ShellCheck;
- URL-матрица для HTTPS, localhost, приватных и публичных HTTP-адресов;
- golden fixtures для неизменности `process_config()`;
- разбор release JSON: точный asset, корректный digest, отсутствующий и
  неоднозначный asset;
- конкурентный запуск с ожидаемым кодом `75`.

Интеграционные тесты используют временный каталог и подменённые `curl`/`systemctl`:

- недоступность GitHub, подписки и Geo;
- неверный digest, битый gzip, битый YAML и ошибка `mihomo -t`;
- независимое обновление ядра со старым профилем и профиля со старым ядром;
- отсутствие остановки сервиса до завершения сетевых операций;
- ошибка старта, автоматический rollback и ручной rollback;
- внешний healthcheck без доступа не откатывает рабочую установку;
- неудачная повторная установка сохраняет старую установку;
- успешная миграция runtime без перезаписи обработанного профиля.

## Критерии готовности

- Рабочий сервис не останавливается во время загрузок и предварительных проверок.
- Битый или несовместимый кандидат не заменяет рабочие файлы.
- Ядро без валидного release digest не устанавливается.
- Одновременно выполняется не более одной изменяющей команды.
- Локальная ошибка после подмены автоматически возвращает known-good комплект.
- Обработка импортируемого профиля совпадает с текущими golden fixtures.
- Потеря одного сетевого источника не нарушает работу текущего прокси и не блокирует
  независимое безопасное обновление другого компонента.
- README и Linux-инструкция соответствуют фактическому поведению.

## Вне области работы

- смена `User=root`;
- systemd sandboxing/hardening;
- изменение правил маршрутизации импортируемого профиля;
- обязательный rollback из-за недоступности внешнего сайта или отдельной ноды.
