# Linux: фоновые обновления Dostup

Дата: 2026-08-20

## Цель

Дважды в неделю без участия пользователя проверять обновления менеджера,
ядра Mihomo, профиля и Geo-баз. Работающий сервис должен останавливаться
только при наличии проверенного изменения. Текущие staging, `mihomo -t`,
локальный healthcheck, known-good и rollback сохраняются.

## Выбранный подход

Использовать отдельные systemd units:

- `dostup-update.service` с `Type=oneshot`;
- `dostup-update.timer` с запуском по понедельникам и четвергам около 04:00;
- случайная задержка до 30 минут;
- `Persistent=true`, чтобы пропущенная проверка выполнялась после загрузки.

Timer автоматически включается при установке и переустановке. Включение
timer не должно немедленно запускать update service. Основной
`dostup.service` и намеренное выполнение Mihomo от root не меняются.

Cron не используется: systemd даёт журнал, состояние последнего запуска,
поддержку пропущенных запусков и естественную интеграцию с существующим
сервисом. Постоянный цикл внутри менеджера не нужен для двух запусков
в неделю.

## Команда фонового обновления

Добавляется внутренняя команда:

```text
dostup update-background
```

Systemd вызывает её через установленный менеджер:

```text
/opt/dostup/dostup-manager.sh --cli update-background
```

Команда:

1. не читает stdin и не требует TTY;
2. получает общий неблокирующий `flock`;
3. проверяет менеджер, Mihomo, профиль и Geo;
4. формирует итоговый staging-кандидат;
5. обрабатывает профиль тем же алгоритмом, что и сейчас;
6. проверяет комбинацию через `mihomo -t`;
7. сравнивает значимые файлы с установленными;
8. завершает работу без перезапуска, если изменений нет;
9. при изменениях использует существующий transactional commit и rollback.

Ручные `dostup restart` и `dostup update` сохраняют текущую семантику.

## Определение изменений

На необходимость commit влияют:

- бинарник `mihomo`;
- обработанный `config.yaml`;
- `GeoIP.dat`, `GeoSite.dat`, `ASN.mmdb`;
- `dostup-manager.sh`;
- управляемые systemd unit-файлы.

Release JSON, журналы проверки, временные файлы и изменения производного
кэша не должны вызывать перезапуск.

Сравнение выполняется только после успешного `mihomo -t`. Если значимых
изменений нет, staging удаляется, в journal записывается соответствующее
сообщение, а `dostup.service` не останавливается.

## Независимые компоненты и ошибки

Сохраняется модель независимых безопасных обновлений:

- недоступный профиль не блокирует проверенное новое ядро;
- недоступный GitHub не блокирует проверенный новый профиль;
- новая комбинация всегда целиком проверяется до подмены;
- недоступность источников сохраняет старые компоненты;
- ошибка локального запуска после commit вызывает rollback;
- внешняя проверка сайта или нод остаётся предупреждением без rollback.

Обычная недоступность источника считается безопасным пропуском, если
установленная версия сохранена и итоговый кандидат исправен. Ненулевой
код нужен при локальной ошибке подготовки/валидации, неисправности после
commit или неудачном rollback.

Если ручная команда уже держит lock, фоновый запуск завершается с кодом
75 и ничего не меняет. Быстрый системный retry не добавляется: сетевые
скачивания уже имеют три попытки, следующая плановая проверка состоится
по расписанию.

## Systemd и журнал

`dostup-update.service`:

- `Type=oneshot`;
- запускается после `network-online.target`;
- выполняется от root;
- имеет ограничение общего времени выполнения, ориентировочно 30 минут;
- пишет stdout/stderr в systemd journal.

`dostup-update.timer`:

- понедельник и четверг около 04:00 по локальной timezone сервера;
- `RandomizedDelaySec` до 30 минут;
- `Persistent=true`;
- устанавливается и включается автоматически.

Диагностика:

```bash
systemctl status dostup-update.timer
systemctl list-timers dostup-update.timer
journalctl -u dostup-update -n 100
sudo systemctl start dostup-update.service
```

Отключение:

```bash
sudo systemctl disable --now dostup-update.timer
```

`dostup uninstall` удаляет основной service, update service и timer.
Переустановка идемпотентно обновляет units и выполняет `daemon-reload`.

## Проверки

Regression-тесты должны покрывать:

- отсутствие чтения stdin и зависимости от TTY;
- отсутствие stop/start при неизменном кандидате;
- commit при изменении только профиля;
- commit при изменении только ядра;
- независимость обновления ядра и профиля при сетевых ошибках;
- отказ кандидата на `mihomo -t` без остановки текущего сервиса;
- rollback после локальной ошибки новой версии;
- код 75 при занятом lock;
- идемпотентную установку timer;
- удаление update units при uninstall;
- `systemd-analyze verify` для всех units.

Существующий побайтовый fixture преобразования профиля остаётся
обязательным. Перед публикацией предоставленный рабочий профиль повторно
проверяется точным Mihomo, но его URL и содержимое не сохраняются в git.
